<objective>
## Goal
Create the async image processing pipeline that generates WebP variants (thumb_200, web_1200, retina_2400), extracts EXIF metadata, computes blurhash, and transitions photos from "processing" to "ready" status.

## Purpose
After Plan 04-01 uploads photos to R2 with status "processing", this plan completes the pipeline by generating optimized variants and enriching photo metadata. Without this, uploaded photos have no viewable variants and remain stuck in "processing" state.

## Output
- `src/lib/processing.ts` — Sharp pipeline: resize, EXIF extraction, blurhash
- `src/lib/storage.ts` — Extended with downloadObject and uploadBuffer
- `src/app/api/uploads/process/route.ts` — POST endpoint running the pipeline
- `src/app/api/uploads/confirm/route.ts` — Modified to trigger processing async
</objective>

<acceptance_criteria>

## AC-1: Variant Generation
```gherkin
Given a photo with status "processing" and an original file in R2
When the processing pipeline runs for that photo
Then three WebP variants are generated: thumb_200 (≤200px wide), web_1200 (≤1200px wide), retina_2400 (≤2400px wide)
And each variant is uploaded to R2 at photos/<uuid>/<variant_type>.webp
And a photo_variants record is created for each with correct width, height, format "webp", and file_size
```

## AC-2: EXIF Extraction and Metadata
```gherkin
Given an original photo with EXIF metadata
When processing runs
Then photos.exif_data is updated with parsed EXIF as JSON
And photos.taken_at is set from EXIF DateTimeOriginal (null if absent)
And photos.width and photos.height are set from original dimensions
```

## AC-3: Blurhash Computation
```gherkin
Given an original photo
When processing runs
Then photos.blurhash is computed and stored as a compact string
```

## AC-4: Status Lifecycle — Success
```gherkin
Given a photo with status "processing"
When processing completes successfully
Then photos.status is updated to "ready"
And photos.updated_at is set to current timestamp
```

## AC-5: Status Lifecycle — Failure
```gherkin
Given a photo with status "processing"
When processing fails (Sharp error, R2 upload failure, etc.)
Then photos.status is updated to "failed"
And the error is logged to console
And the photo is NOT left in "processing" state indefinitely
```

## AC-6: Async Trigger from Confirm
```gherkin
Given a photo upload is confirmed via POST /api/uploads/confirm
When the confirm endpoint returns 200 with { id, status: "processing" }
Then the processing endpoint is triggered asynchronously
And the confirm response returns before processing completes
```

## AC-7: Process Endpoint Auth
```gherkin
Given an unauthenticated request
When accessing POST /api/uploads/process
Then response is 401 JSON { data: null, error: "Unauthorized" }
```

<task type="auto">
  <name>Task 1: Add storage helpers, install processing dependencies, create Sharp pipeline</name>
  <files>package.json, pnpm-lock.yaml, src/lib/storage.ts, src/lib/processing.ts</files>
  <action>
    1. Install dependencies and move sharp:
       ```
       pnpm add blurhash exif-reader
       pnpm add sharp && pnpm remove -D sharp
       ```
       Note: sharp is currently in devDependencies (legacy optimize-images script). Move to dependencies for production use.

    2. Extend `src/lib/storage.ts` with two new functions:
       - `downloadObject(storageKey: string)`: returns `Promise<Buffer>`
         - Uses GetObjectCommand to download from R2
         - Converts response Body stream to Buffer using async iterator: `for await (const chunk of response.Body) { chunks.push(chunk) }` → `Buffer.concat(chunks)` <!-- audit-added: explicit pattern -->
         - Guard: throw if response.Body is undefined <!-- audit-added -->
         - Import GetObjectCommand from @aws-sdk/client-s3
       - `uploadBuffer(storageKey: string, buffer: Buffer, contentType: string)`: returns `Promise<void>`
         - Uses PutObjectCommand to upload buffer to R2
         - Sets ContentType and ContentLength

    3. Create `src/lib/processing.ts`:
       - `processPhoto(photoId: string, storageKey: string)`: main orchestrator
         - Downloads original from R2 via downloadObject()
         - Calls generateVariants(), extractMetadata(), computeBlurhash() in parallel where possible
         - Uploads each variant to R2
         - Returns ProcessingResult with all metadata and variant info
         - On any error, throws (caller handles status update)

       - `generateVariants(originalBuffer: Buffer, photoId: string)`: returns `Promise<VariantResult[]>`
         - For each entry in VARIANT_CONFIGS (thumb_200, web_1200, retina_2400):
           - Use sharp(originalBuffer).resize({ width: maxWidth, withoutEnlargement: true }).webp({ quality: 80 })
           - Get output buffer and metadata (width, height)
           - Build storage key: `photos/${photoId}/${variantType}.webp`
           - Return: { variantType, storageKey, buffer, width, height, format: "webp", fileSize: buffer.length }
         - withoutEnlargement: true prevents upscaling small originals

       - `extractMetadata(originalBuffer: Buffer)`: returns `Promise<{ width, height, exifData, takenAt }>`
         - Use sharp(originalBuffer).metadata() for width, height, and raw exif buffer
         - If exif buffer exists, parse with `exifReader(metadata.exif)` (default import from exif-reader)
         - **EXIF date quirk:** DateTimeOriginal is a string in format `"YYYY:MM:DD HH:MM:SS"` (colons in date part). Parse by replacing first two colons: `dateStr.replace(/^(\d{4}):(\d{2}):/, '$1-$2-')` then `new Date()`. Return null if absent or unparseable. <!-- audit-added -->
         - **Sanitize for JSONB:** exif-reader output may contain Buffer objects (e.g., thumbnail data) and non-serializable values. Recursively strip Buffers and convert Dates to ISO strings before storing as exifData. Use `JSON.parse(JSON.stringify(data))` as a safety net, or write explicit sanitizer. <!-- audit-added -->
         - Return exifData as JSON-serializable object, takenAt as Date or null

       - `computeBlurhash(originalBuffer: Buffer)`: returns `Promise<string>`
         - Use sharp(originalBuffer).resize(32, 32, { fit: "inside" }).ensureAlpha().raw().toBuffer({ resolveWithObject: true })
         - Get raw pixel data ({ data, info: { width, height } })
         - **CRITICAL:** Convert Buffer to Uint8ClampedArray before passing to blurhash: `new Uint8ClampedArray(data)` — blurhash.encode() expects Uint8ClampedArray, not Buffer. TypeScript will reject Buffer here. <!-- audit-added -->
         - Use encode(uint8Data, width, height, 4, 3) for a compact hash
         - Return the blurhash string

    Avoid:
    - Do NOT process synchronously in the confirm endpoint (CLAUDE.md: "Don't process images synchronously in API routes")
    - Do NOT use sharp's toFile() — always use toBuffer() since we upload to R2, not local disk
    - Do NOT strip EXIF from the original — only variants are processed. The original stays as-is in R2
    - Do NOT make EXIF parsing a hard failure — missing/corrupt EXIF should result in null exifData, not a crash
  </action>
  <verify>

    - `sharp`, `blurhash`, `exif-reader` appear in package.json dependencies (not devDependencies for sharp)
    - storage.ts exports: downloadObject, uploadBuffer (in addition to existing exports)
    - processing.ts exports: processPhoto, generateVariants, extractMetadata, computeBlurhash
  </verify>
  <done>AC-1 partially (variant generation logic), AC-2 partially (EXIF extraction logic), AC-3 partially (blurhash logic)</done>

<task type="auto">
  <name>Task 2: Create process endpoint and wire async trigger from confirm</name>
  <files>src/app/api/uploads/process/route.ts, src/app/api/uploads/confirm/route.ts</files>
  <action>
    1. Create `src/app/api/uploads/process/route.ts` (POST):
       - Add `export const dynamic = "force-dynamic"` and `export const maxDuration = 60` (allow up to 60s for Sharp processing on Vercel)
       - Call getSession() — return 401 JSON if null
       - Parse JSON body: `{ photoId: string }`
       - Validate photoId is present — return 400 if missing
       - Query photo record by ID — return 404 if not found
       - Verify photo status is "processing" — return 400 if not (prevents re-processing)
       - Call processPhoto(photoId, photo.storageKey) from processing.ts:
         - On success:
           - Update photos record: width, height, exifData, blurhash, takenAt, status → "ready", updatedAt → now
           - Insert photo_variants records for all three variants
           - Return 200: `{ data: { id, status: "ready", variants: count }, error: null }`
         - On failure (catch block):
           - Update photos.status → "failed"
           - Log error details
           - Return 500: `{ data: null, error: "Processing failed" }`
       - The status update to "failed" MUST be in a finally or catch — never leave a photo in "processing" after an error

    2. Modify `src/app/api/uploads/confirm/route.ts`:
       - After the successful photo record INSERT (inside the try block, before the return statement):
       - Add a fire-and-forget fetch to trigger processing:
         ```typescript
         const processUrl = new URL("/api/uploads/process", request.url);
         fetch(processUrl, {
           method: "POST",
           headers: {
             "Content-Type": "application/json",
             Cookie: request.headers.get("cookie") ?? "",
           },
           body: JSON.stringify({ photoId }),
         }).catch((err) => console.error("Failed to trigger processing:", err));
         ```
       - Forward the Cookie header so the process endpoint can authenticate the request
       - Do NOT await the fetch — the confirm response returns immediately
       - The .catch() prevents unhandled rejection if the fetch itself fails to send

    Avoid:
    - Do NOT await the processing fetch in confirm — that would make it synchronous
    - Do NOT skip the status → "failed" update on processing errors
    - Do NOT re-process photos that are already "ready" or "failed"
    - Do NOT use request.url for the process URL if it might resolve to localhost in production — use a relative path via new URL()
  </action>
