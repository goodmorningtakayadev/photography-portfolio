<objective>
## Goal
Build the admin layout shell, dashboard overview, and photo management page — establishing the core admin experience for the photography CMS.

## Purpose
The admin interface is the central value proposition of the CMS. Without it, the photographer cannot manage their portfolio from the browser. This plan delivers the most critical pieces: navigation, at-a-glance status, and full photo lifecycle management including the deferred Phase 4 issue of re-processing failed photos.

## Output
- Admin layout with responsive sidebar navigation
- Dashboard with photo statistics and recent uploads
- Photo management page with status filtering, metadata editing, category assignment, and lifecycle actions (publish, archive, restore, delete, re-process)
- Admin-specific database query functions
- Photo mutation API route with delete cascade following CLAUDE.md checklist
</objective>

## AC-4: Photo Management Actions
```gherkin
Given the admin clicks edit on a photo
When the modal opens
Then fields for caption, alt_text, gallery_sort_order, and category multi-select are shown with current values
And saving persists all changes via PATCH /api/photos/[id]

Given the admin toggles publish on a photo
When the action completes
Then is_published flips and the grid refreshes

Given the admin archives a ready photo
When the action completes
Then status changes to "archived", any projects.cover_photo_id references are nulled, and the grid refreshes

Given the admin restores an archived photo
When the action completes
Then status changes to "ready" and the grid refreshes

Given the admin permanently deletes a photo (with confirmation)
When the action completes
Then R2 files (original + all variants) are deleted before the database row, the photos row is deleted (cascading to join tables), and the photo disappears from the grid

Given a photo has status "failed" and the admin clicks re-process
When the action completes
Then existing variant records are deleted, status is set to "processing", and the processing pipeline is re-triggered via fire-and-forget
```

    - Client component ("use client")
    - Props: photos array (with thumbStorageKey), categories array, pagination info, current status filter
    - Filter tabs at top: All, Ready, Processing, Failed, Archived
      - Clicking a tab calls router.push with updated ?status= param (or removes it for "All")

    - Responsive grid: 2 cols on mobile, 3 on tablet (md:), 4+ on desktop (lg:)
    - Each photo card:
      - Thumbnail image: `${NEXT_PUBLIC_CDN_URL}/${thumbStorageKey}` or neutral placeholder
      - Caption (fallback: "Untitled"), StatusBadge, published dot/icon
      - Action buttons row: Edit, Publish/Unpublish toggle, Archive (or Restore if archived), Delete, Re-process (only visible when status="failed")
    - Action handlers call fetch() to PATCH/DELETE /api/photos/[id], then router.refresh()
    - Delete action: show confirmation dialog (window.confirm or custom modal) before calling DELETE
    - Pagination at bottom: Previous/Next buttons + page indicator, updating ?page= param

    **Photo edit modal (`src/components/admin/PhotoEditModal.tsx`):**
    - Client component, controlled via open/onClose props
    - Form fields: caption (input), altText (textarea), gallerySortOrder (number input), categories (checkbox list from categories prop)
    - Pre-populated with current photo values
    - Save button: PATCH /api/photos/[id] with changed fields, call onSave callback on success
    - Loading state on save button, error display on failure
    - Accessible: focus trap, Escape key closes, aria-labelledby, role="dialog"

    **Photo API route (`src/app/api/photos/[id]/route.ts`):**
    - Auth on all handlers: `const session = await getSession(); if (!session) return NextResponse.json({ error: "Unauthorized" }, { status: 401 })`
    - Response shape: `{ data: T } | { error: string }`

    PATCH handler:
    - Parse body with Zod: `{ caption?, altText?, gallerySortOrder?, isPublished?, categoryIds?: string[], action?: "archive" | "restore" | "reprocess" }`
    - Standard field updates: update photos row with provided fields (caption, altText, gallerySortOrder, isPublished) + set updatedAt
    - If categoryIds provided: delete all photo_categories where photoId matches, then insert new rows for each categoryId
    - If action="archive": set status to "archived", query projects for cover_photo_id matching this photo → set to null
    - If action="restore": set status to "ready"
    - If action="reprocess": verify current status is "failed", delete photo_variants rows for this photo, set status to "processing", fire-and-forget fetch to /api/uploads/process with { photoId, storageKey } and cookie forwarding (same pattern as confirm endpoint)
    - Return updated photo

    DELETE handler:
    - Require `{ confirm: true }` in request body
    - Follow CLAUDE.md permanent delete cascade:
      1. Fetch photo row (get storageKey) and all photo_variants (get variant storageKeys)
      2. Query projects where cover_photo_id = this photo → set cover_photo_id to null
      3. Delete all variant files from R2: loop deleteObject(variant.storageKey) — collect errors, don't abort on individual failures
      4. Delete original from R2: deleteObject(photo.storageKey)
      5. Delete photos row (ON DELETE CASCADE handles photo_categories, project_photos, photo_variants)
      6. Note: revalidateTag deferred to Phase 6
    - If any R2 deletions fail: log the orphaned keys, still delete DB row, include warning in response
    - Return `{ data: { deleted: true, orphanedKeys?: string[] } }`

    Avoid:
    - Don't use raw SQL for writes — Drizzle query builder only
    - Don't process images synchronously in the API route — use fire-and-forget for re-process
    - Don't hard-delete without { confirm: true } — reject requests without confirmation
    - Don't store URLs in database — storage keys only, resolve CDN URL in components
    - Don't modify existing upload endpoint behavior
