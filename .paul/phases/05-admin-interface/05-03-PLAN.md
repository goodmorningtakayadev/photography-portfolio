<objective>
## Goal
Build project CRUD management with photo ordering (drag-and-drop), cover photo selection, and bulk photo operations (multi-select archive, multi-select categorize) to complete the admin interface.

## Purpose
Projects are curated, ordered photo collections with their own identity and viewing UX. The admin needs to create, edit, publish, and organize projects — including ordering photos within them via drag-and-drop. Bulk operations reduce repetitive per-photo actions when managing large photo libraries.

## Output
- Project API routes (CRUD + photo management)
- Project list page with create/edit/delete/publish
- Project editor page with photo ordering (drag-and-drop) and cover photo selection
- Bulk operations on the photo grid (multi-select, bulk archive, bulk categorize)
</objective>

## AC-1: Project CRUD
```gherkin
Given the admin is authenticated
When they navigate to /admin/projects
Then they see a list of all projects with title, photo count, published state, and cover photo thumbnail

Given the admin clicks "New Project"
When they enter a title and save
Then a project is created with auto-generated slug, unpublished state, and sort_order at the end
And they are redirected to the project editor page

Given the admin is on a project's editor page
When they update the title, description, or slug and save
Then the project is updated in the database
And slug uniqueness is enforced (409 on conflict)

Given the admin clicks delete on a project
When they confirm the deletion
Then the project and all project_photos join rows are deleted (ON DELETE CASCADE)
And the project disappears from the list
```

## AC-2: Project Photo Management
```gherkin
Given the admin is on a project's editor page
When they click "Add Photos"
Then a photo picker modal shows all ready, published photos not already in the project
And they can select multiple photos and add them to the project

Given a project has photos
When the admin drags a photo to a new position
Then the sort_order values are updated in project_photos
And the new order persists on page refresh

Given a project has photos
When the admin clicks "Set as Cover" on a photo
Then that photo's ID is saved as the project's cover_photo_id
And the cover photo is visually indicated in the editor

Given the admin clicks remove on a project photo
When confirmed
Then the project_photos join row is deleted
And the photo itself is NOT deleted (only removed from this project)
And if the removed photo was the cover, cover_photo_id is set to null
```

## AC-3: Bulk Photo Operations
```gherkin
Given the admin is on the photos page
When they click "Select" to enter selection mode
Then checkboxes appear on each photo card
And a floating action bar shows with count and available actions

Given the admin has selected multiple photos
When they click "Archive Selected"
Then all selected photos are archived in a single transaction
And the UI refreshes showing updated statuses

Given the admin has selected multiple photos
When they click "Set Categories" and select categories from the picker
Then all selected photos have their categories REPLACED with the chosen set (not appended)
And the UI refreshes
And the UI label makes clear this is a replace operation ("Set Categories" not "Add Categories") <!-- audit-added: clarify replace semantics -->
```

  <action>
    **API Routes:**

    1. `src/app/api/projects/route.ts`:
       - GET: List all projects with photo count and cover photo thumb URL. Join projects → project_photos (count), left join photos → photo_variants (cover thumb). Order by sort_order ASC.
       - POST: Create project. Accept `{ title }`. Auto-generate slug from title (duplicate slugify from categories route, truncate to 200 chars to match schema). Auto-assign sort_order = max + 1. Return created project. 409 on slug/title conflict.

    2. `src/app/api/projects/[id]/route.ts`:
       - GET: Fetch project with all its photos (joined with thumb variants), ordered by project_photos.sort_order. Include cover photo info.
       - PATCH: Update project fields `{ title?, description?, slug?, isPublished?, coverPhotoId?, sortOrder? }`. Zod validation. If title changes and slug not explicitly provided, auto-regenerate slug. If isPublished set to true, also set publishedAt = now(). 409 on slug conflict. If coverPhotoId is provided, verify the photo exists in the project's project_photos join table — return 400 if the photo is not part of this project. <!-- audit-added: validate coverPhotoId belongs to project -->
       - DELETE: Delete project. Requires `{ confirm: true }`. ON DELETE CASCADE handles project_photos. Do NOT delete photos themselves. Return success.

    3. `src/app/api/projects/[id]/photos/route.ts`:
       - POST: Add photos to project. Accept `{ photoIds: string[] }`. Validate all photoIds reference existing photos with status = "ready" before inserting — return 400 with details for any invalid IDs. Insert into project_photos with sort_order = max existing + 1, +2, +3... for each. Ignore duplicates (skip if already in project via ON CONFLICT DO NOTHING or pre-filter). Return added count. <!-- audit-added: validate photoIds exist -->
       - PUT: Reorder photos. Accept `{ photoIds: string[] }` as the full ordered list. Reject empty arrays with 400 — an empty reorder would delete all photos from the project. <!-- audit-added: guard empty array --> Use `db.batch()` to atomically delete all project_photos for this project and re-insert with new sort_order values (index-based). **CRITICAL: neon-http does NOT support `db.transaction()` — use `db.batch()` instead, which sends both queries as a single atomic HTTP transaction to Neon.** Without batch, a failure between delete and insert would orphan the project with zero photos. <!-- audit-added: batch for atomicity -->
       - DELETE: Remove photo from project. Accept `{ photoId: string }`. Delete project_photos row. If removed photo was cover_photo_id, set cover_photo_id to null. Do NOT delete the photo itself.

    All routes: `export const dynamic = "force-dynamic"`, getSession() auth, `{ data, error }` response shape, Zod validation.

    **Query Functions (src/db/queries/admin.ts):**

    4. Add `getAllProjectsAdmin()`: Select all projects with photo count (left join project_photos + count) and cover photo thumb storage key (left join photos → photo_variants where variant_type = thumb_200). Order by sort_order ASC.

    5. Add `getProjectByIdAdmin(id)`: Select project by ID, then fetch its photos with thumb variants, ordered by project_photos.sort_order.

    **Admin Pages:**

    7. `src/app/admin/projects/new/page.tsx`: Server component. Render heading "New Project" + form to create a project. On create, redirect to /admin/projects/[id].

    8. `src/app/admin/projects/[id]/page.tsx`: Server component. Fetch project via getProjectByIdAdmin(id). 404 if not found. Also fetch all ready photos with thumb variants (using a new `getReadyPhotosWithThumb()` query or reusing `getAllPhotosAdmin({ status: "ready" })`) to pass as `availablePhotos` prop to ProjectEditor — the photo picker modal needs this data and the client component cannot fetch it server-side. <!-- audit-added: photo picker data source --> Render ProjectEditor client component with project data, available photos, and all categories.

    **Client Components:**

    9. `src/components/admin/ProjectList.tsx`: Card grid showing projects. Each card shows cover photo thumb (or placeholder), title, photo count, published badge, sort order. Action overlay on hover with Edit (link to /admin/projects/[id]), publish/unpublish toggle, delete with confirm. Follow same Dark Cinematic Brutalism patterns as PhotoGrid — same card structure, StatusBadge-like published indicator, mono labels.

    10. `src/components/admin/ProjectEditor.tsx`: Two-section layout:
        - **Left panel (details):** Title input, slug input (auto-generated from title, editable), description textarea, publish toggle, save button. Follow same form styling as PhotoEditModal.
        - **Right panel (photos):** Photo grid within the project, ordered by sort_order. Each photo shows thumb + "Set as Cover" button + "Remove" button. Cover photo has visual indicator (ember border). "Add Photos" button opens a photo picker modal. The picker receives `availablePhotos` from server props and filters out photos already in the project client-side. Multi-select with "Add Selected" button. <!-- audit-added: picker uses server-provided data -->
        - **Drag-and-drop reorder:** Use native HTML drag events on the photo items (same approach as UploadDropzone drag events — no external libraries). On dragstart, capture source index. On dragover, show drop indicator. On drop, compute new order, call PUT /api/projects/[id]/photos with full reordered list. Optimistic update with revert on error.
        - "Back to Projects" link at top.

    **Design:** Match established Dark Cinematic Brutalism — Syne headings, JetBrains Mono labels, ember teal accents, warm dark backgrounds, frosted borders. Use same CSS variables (--black, --ember, --border, --white-ghost, etc.) and transition patterns (var(--t-fast), var(--ease-out)) as existing admin components.

       - POST: Accept `{ action: "archive" | "categorize", photoIds: string[], categoryIds?: string[] }`. Zod validation.
       - For "archive": Use `db.batch()` to atomically: (1) update all matching photos to status = "archived", (2) clear cover_photo_id on any projects referencing these photos. Return { updated: count }. <!-- audit-added: batch for atomicity -->

Use `db.batch()` to atomically execute all deletes and inserts in a single HTTP transaction — CLAUDE.md requires "batch their database writes in a single transaction" for bulk operations. Collect all DELETE and INSERT queries, then send via `db.batch([...deletes, ...inserts])`. Return { updated: count }. <!-- audit-added: batch atomicity + replace semantics clarification -->
