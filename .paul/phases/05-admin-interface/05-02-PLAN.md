<objective>
## Goal
Build the upload interface (drag-and-drop, multi-file, progress tracking, processing status) and category management page (CRUD, reorder) for the admin CMS.

## Purpose
These are the two remaining content-input features the admin needs before project management. Without an upload UI, the admin cannot add photos. Without category management, the admin cannot create or organize the filter labels used on the gallery page.

## Output
- `/admin/upload` page with drag-and-drop multi-file upload, per-file progress bars, and real-time processing status
- `/admin/categories` page with category list, add/edit/delete, and drag-and-drop reordering
- Category API routes (GET, POST, PATCH, DELETE, bulk reorder)
</objective>

## AC-1: Multi-File Drag-and-Drop Upload
```gherkin
Given the admin is on /admin/upload
When they drag one or more image files onto the dropzone (or click to browse)
Then each file is validated against ALLOWED_UPLOAD_TYPES and MAX_UPLOAD_SIZE
And valid files appear in an upload queue with filename and thumbnail preview
And invalid files show an inline error (wrong type or too large) without blocking valid files
```

## AC-2: Upload Progress and Processing Status
```gherkin
Given files are in the upload queue
When the admin initiates upload
Then each file progresses through stages: presigning → uploading → confirming → processing
And each file shows a progress bar during the R2 upload (via XMLHttpRequest progress events)
And after confirmation, each file polls for status until "ready" or "failed"
And completed files show a success indicator with thumb_200 preview
And failed files show an error indicator with option to retry
And if any stage fails (network error, server error), the error message indicates which stage failed <!-- audit-added -->
And navigating away while uploads are active triggers a beforeunload warning <!-- audit-added -->
```

## AC-3: Category CRUD
```gherkin
Given the admin is on /admin/categories
When they add a new category (name input)
Then the slug is auto-generated from the name (lowercase, hyphenated)
And the category appears in the list with the next sort order
And validation prevents duplicate names/slugs

Given an existing category
When the admin edits its name
Then the slug updates automatically
And the change persists to the database

Given an existing category
When the admin deletes it
Then a confirmation prompt appears
And on confirm, the category and its photo_categories associations are deleted (CASCADE)
And the category disappears from the list
```

## AC-4: Category Reordering
```gherkin
Given the admin is on /admin/categories with multiple categories
When they drag a category to a new position (or use up/down controls)
Then the sort_order values are recalculated for all affected categories
And the new order persists via a bulk update API call
And the list reflects the new order immediately (optimistic update)
```

  <name>Task 1: Upload interface with drag-and-drop, progress tracking, and processing status</name>
  <files>src/app/admin/upload/page.tsx, src/components/admin/UploadDropzone.tsx</files>
  <action>
    **Page (server component):**
    Create `src/app/admin/upload/page.tsx` with `export const dynamic = "force-dynamic"` and metadata title "Upload". Renders a heading and the UploadDropzone client component.

    **UploadDropzone (client component):**
    Create `src/components/admin/UploadDropzone.tsx` with `"use client"`:

    1. **Drop zone**: Full-width dashed border area. Accept drag-and-drop and click-to-browse. Use native HTML drag events (dragenter/dragover/dragleave/drop) — no external drag library.

    2. **File validation**: On file selection, validate each against ALLOWED_UPLOAD_TYPES (check MIME type) and MAX_UPLOAD_SIZE. Show inline errors for rejected files without blocking valid ones. Import the constants from `@/lib/constants`.

    3. **Upload queue state**: Each file tracks its own state:
       ```
       type UploadItem = {
         id: string;          // crypto.randomUUID()
         file: File;
         preview: string;     // URL.createObjectURL
         status: 'queued' | 'presigning' | 'uploading' | 'confirming' | 'processing' | 'ready' | 'failed';
         progress: number;    // 0-100 for upload phase
         error?: string;
         photoId?: string;    // from presign response
         thumbUrl?: string;   // CDN URL for thumb_200 after ready
       }
       ```

    4. **Upload pipeline per file** (sequential stages):
       - **Presign**: `GET /api/uploads/presign?filename=<name>&contentType=<type>` → get `{ url, storageKey, photoId }`
       - **Upload to R2**: PUT to presigned URL with the file body. Use XMLHttpRequest for progress events (onprogress). Set Content-Type header matching what was presigned. Set `xhr.timeout = 300000` (5 minutes) to prevent indefinite hangs on large files/slow connections. On timeout, abort and set status to 'failed' with error "Upload timed out". <!-- audit-added: upload timeout -->
       - **Confirm**: `POST /api/uploads/confirm` with `{ storageKey }` → triggers processing
       - **Poll for processing**: After confirm, poll `GET /api/photos/<photoId>` every 2 seconds until status is "ready" or "failed". Stop polling after 120 seconds (timeout → show as failed). On "ready", construct `thumbUrl` as `${process.env.NEXT_PUBLIC_CDN_URL}/photos/${photoId}/thumb_200.webp` — do NOT parse variants from the API response. This follows CLAUDE.md's pattern of resolving CDN URLs at render time from known storage key patterns. <!-- audit-added: CDN URL construction -->
       - **Error handling per stage**: Wrap each stage in try-catch. On failure, set status to 'failed' with a stage-specific error message (e.g., "Presign failed: server returned 500", "Upload failed: network error", "Confirm failed: file not found in storage"). This lets the admin diagnose issues without guessing which stage broke. <!-- audit-added: per-stage errors -->

    5. **UI for each queue item**: Show file preview thumbnail, filename, status badge (use StatusBadge-style coloring), progress bar during upload, and final state (thumb_200 from CDN or error message). Failed items show a "Retry" button that resets to "queued" and re-runs the pipeline.

    6. **Start upload**: Button to begin uploading all queued files. Process files concurrently (max 3 at a time to avoid overwhelming the server). Disable the start button while uploads are in progress.

    7. **Cleanup**: Revoke object URLs on unmount. Clear completed items with a "Clear completed" button.

    8. **Navigation guard**: Register a `beforeunload` event listener while any files have an active status ('presigning' | 'uploading' | 'confirming' | 'processing'). This prevents accidental navigation that would orphan R2 files (presigned but unconfirmed). Remove the listener when all files reach terminal status ('ready' | 'failed' | 'queued') or on component unmount. <!-- audit-added: beforeunload -->

    **Styling**: Follow 05-01 Dark Cinematic Brutalism patterns:
    - Mono uppercase labels (JetBrains Mono, 0.6-0.7rem, tracking 0.15em)
    - Ember teal accent (var(--ember)) for active/success states
    - Warm dark backgrounds (var(--black), rgba(11,11,11,...))
    - Frosted glass borders (var(--border))
    - CSS transitions using var(--t-fast), var(--t-base), var(--ease-out)

    **Avoid:**
    - No external libraries for drag-and-drop (react-dropzone, etc.) — native events only
    - No external progress bar libraries — simple CSS width transition
    - Do NOT modify existing upload API routes — they already work correctly
  </action>

  <name>Task 2: Category API routes and management page</name>
  <files>src/app/api/categories/route.ts, src/app/api/categories/[id]/route.ts, src/app/admin/categories/page.tsx, src/components/admin/CategoryManager.tsx, src/db/queries/admin.ts</files>
  <action>
    **Category query functions** — add to `src/db/queries/admin.ts`:
    - `getAllCategories()`: Select all categories ordered by sortOrder. Include count of photos in each category (left join photo_categories, group by).
    - `getCategoryById(id)`: Single category lookup.

    **Category API — `/api/categories/route.ts`:**
    - `GET`: Return all categories with photo count, ordered by sortOrder. Auth via getSession().
    - `POST`: Create a new category. Body: `{ name: string }`. Zod validation: trim whitespace, min 1 char, max 100 chars (matching schema varchar(100)). Auto-generate slug from name (lowercase, replace spaces/special chars with hyphens, collapse multiples). Set sortOrder to max(sortOrder) + 1. Validate uniqueness of name and slug (catch Postgres unique constraint error, return 409). Return created category. <!-- audit-added: name validation constraints -->

    **Category API — `/api/categories/[id]/route.ts`:**
    - `PATCH`: Update category. Body can include `{ name?, slug?, sortOrder? }`. If name changes and slug not explicitly provided, auto-regenerate slug. Zod validation. Handle unique constraint conflicts (409).
    - `DELETE`: Delete category by ID. Responds 204 on success. FK CASCADE handles photo_categories cleanup.

    **Slug generation helper**: Create a `slugify` function within the categories route file (or inline). Convert to lowercase, replace non-alphanumeric with hyphens, collapse consecutive hyphens, trim leading/trailing hyphens. Handle edge cases: if slug result is empty after stripping (input was all special characters), return 400 with "Name must contain at least one alphanumeric character". Truncate slug to 100 chars to match schema varchar(100). <!-- audit-added: slugify edge cases -->

    **Bulk reorder**: The PATCH endpoint on individual categories handles sortOrder. The CategoryManager client will send individual PATCH requests for each moved item, OR use a sequence of PATCH calls. Keep it simple — no separate bulk endpoint needed since the category set is small (typically <15 items).

    **Category management page** — `src/app/admin/categories/page.tsx`:
    Server component with `export const dynamic = "force-dynamic"`. Fetch categories via getAllCategories(). Render heading and pass data to CategoryManager client component.

    **CategoryManager client component** — `src/components/admin/CategoryManager.tsx`:
    `"use client"` component receiving initial categories as props.

    1. **Category list**: Ordered list showing each category with name, slug (dimmed), photo count, and action buttons (edit, delete, move up/down).

    2. **Add category**: Input field at the top with "Add" button. Shows slug preview as user types. On submit, POST to /api/categories, add to local state on success.

    3. **Edit category**: Inline edit mode — clicking edit replaces the name with an input field. Save on Enter or blur. PATCH to /api/categories/[id].

    4. **Delete category**: Confirmation dialog before DELETE. Show the photo count in the warning ("This will remove the category from N photos").

    5. **Reorder**: Up/down arrow buttons for each category. On click, swap sortOrder with adjacent category. PATCH both affected categories. Optimistic update — reorder in state immediately, revert on error. First/last items disable up/down respectively.

    **Styling**: Same Dark Cinematic Brutalism patterns as Task 1.
    - Category list items with border-bottom var(--border)
    - Mono uppercase for slugs and labels
    - Ember accent for action buttons on hover
    - Subtle hover state for list rows

    **Avoid:**
    - Do NOT add description, cover photo, or any metadata to categories (CLAUDE.md constraint — categories are flat filter labels)
    - Do NOT use drag-and-drop for reordering categories — up/down buttons are sufficient for a small list (<15 items). Save drag-and-drop for project photo ordering in 05-03.
    - Do NOT modify the categories schema — it already has everything needed
  </action>
