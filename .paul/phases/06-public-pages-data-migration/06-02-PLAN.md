<objective>
## Goal
Create public-facing project listing and individual project pages with their own UX flow, and wire ISR revalidation into all admin mutation endpoints so content changes propagate to the public site.

## Purpose
Projects are curated, ordered photo collections with their own identity — they deserve dedicated pages, not a tab in the gallery. ISR revalidation ensures admin changes (publish, edit, reorder) are reflected on the public site within seconds instead of waiting for the 1-hour TTL.

## Output
- /projects listing page showing published projects with cover photos
- /projects/[slug] detail page showing project description + ordered photo grid with lightbox
- revalidateTag calls in all admin mutation endpoints
- generateStaticParams for project detail pages
</objective>

    **Project Detail Component (`src/page-components/ProjectDetailPage.tsx`):**

    4. New client component (`'use client'`). **Hybrid Magazine Layout** — an editorial viewing experience, NOT a standard gallery grid or lightbox.

       **Structure: Scroll-snapping editorial sections**
       - The page is a vertical scroll with CSS `scroll-snap-type: y mandatory` on the container
       - Each "section" snaps to the viewport — one spread per screen
       - Photos are assigned to layout templates based on their position in the project's ordered list

       **Layout Templates (cycle through based on index):**
       - **Title Card** (first section): Project title (Syne, oversized), description (Outfit), photo count, published date. Full viewport height. Dark background with subtle neon accent line (matching homepage hero). A "scroll to begin" indicator at bottom.
       - **Hero Spread**: Single photo, full-bleed edge-to-edge, 100vh. Use `photo.url` (original) for maximum quality — PhotoView has no retina_2400 field, and the original is full-res. <!-- audit-added: use original for hero, not non-existent retina field --> Minimal caption overlaid at bottom-left with frosted glass bar. For high-impact opening shots.
       - **Diptych**: Two photos side-by-side, each ~50vw. Slight vertical offset between them for editorial asymmetry. Captions below each. On mobile, stack vertically (each photo full-width, still snapped as one section).
       - **Editorial**: Photo on one side (~60%), text column on other (~40%) with large pull-quote caption, photo metadata (date, category), and a decorative rule line. Alternates left/right.
       - **Detail**: Centered photo at ~70% width with generous negative space on all sides. Large mono caption below. Breathing room between dense spreads.

       **Template assignment (algorithmic, not manual):**
       - Section 0: Always Title Card
       - Section 1: Always Hero Spread (first photo — strongest visual)
       - Sections 2+: Cycle through [Diptych, Editorial, Detail, Hero] based on remaining photo count. **Diptych consumes 2 photos per section** — track a photo cursor/index and advance by 2 for Diptych, 1 for others. If fewer than 2 photos remain when Diptych is next, skip to Editorial or Detail. <!-- audit-added: clarify photo consumption -->
       - Last section: "End card" — project title repeated small, "← Back to Projects" link, "Next Project" link if one exists

       **Interactions:**
       - Scroll-snap between sections (CSS scroll-snap-align: start)
       - Scroll-triggered reveals: each section fades in as it enters viewport (useRevealAll or IntersectionObserver)
       - Subtle parallax on Hero Spread photos (same pattern as homepage hero)
       - NO lightbox — the editorial layout IS the viewing experience
       - Keyboard navigation: ArrowDown/ArrowUp scroll to next/prev section
       - Progress indicator: thin vertical line on right edge showing scroll position (mono, --ember color)

       **Typography & Design:**
       - Title Card: Syne, oversized (clamp 3rem → 8rem), uppercase, tight tracking
       - Pull quotes: Syne italic or Outfit light, larger than body
       - Captions: JetBrains Mono, 10-11px, uppercase tracking, --white-ghost color
       - All section backgrounds: --black (consistent with site)
       - Ember accents on progress indicator, decorative rules, hover states
       - Frosted glass caption bars: rgba(11,11,11,0.75), backdrop-blur

       **Responsive:**
       - Desktop: Full editorial layouts with diptychs and side-by-side editorial. `scroll-snap-type: y mandatory`.
       - Tablet: Diptychs become stacked, editorial photo becomes full-width with text below. `scroll-snap-type: y proximity`.
       - Mobile: All layouts stack vertically, each photo full-width. **Use `scroll-snap-type: y proximity`** (not mandatory) — mandatory snap hijacks natural mobile scrolling and creates a frustrating UX. Proximity snaps when close to a boundary but allows fluid scrolling otherwise. <!-- audit-added: proximity snap on mobile -->

       **Accessibility:**
       - All photos have alt text (from photo.altText || photo.caption)
       - Scroll-snap sections use aria-label describing the spread
       - Progress indicator is decorative (aria-hidden)
       - Keyboard ArrowDown/Up for section navigation
       - prefers-reduced-motion: disable parallax, use instant snap instead of smooth scroll

  <action>
    **CRITICAL: Use `revalidatePath` NOT `revalidateTag`.** Drizzle queries go directly to the database, not through Next.js `fetch` cache. `revalidateTag` only invalidates `fetch`-based or `unstable_cache`-wrapped data. Since our pages use direct Drizzle queries, `revalidateTag` would be a no-op. `revalidatePath` directly invalidates the ISR-cached page, forcing regeneration on next request. <!-- audit-added: revalidateTag doesn't work with Drizzle queries -->

    Add `import { revalidatePath } from "next/cache";` to each admin API route file and call it after successful mutations:

    **Photo mutations (`src/app/api/photos/[id]/route.ts`):**
    1. PATCH (publish/unpublish, archive, restore): `revalidatePath('/')` + `revalidatePath('/gallery')` after success
    2. PATCH (category assignment): `revalidatePath('/gallery')` after success
    3. DELETE: `revalidatePath('/')` + `revalidatePath('/gallery')` after success. Also revalidate affected project pages — query project slugs containing this photo, call `revalidatePath('/projects/' + slug)` for each. Also `revalidatePath('/projects')`.

    **Bulk mutations (`src/app/api/photos/bulk/route.ts`):**
    4. archive action: `revalidatePath('/')` + `revalidatePath('/gallery')` after success
    5. restore action: `revalidatePath('/')` + `revalidatePath('/gallery')` after success
    6. categorize action: `revalidatePath('/gallery')` after success

    **Project mutations (`src/app/api/projects/route.ts`):**
    7. POST (create): `revalidatePath('/projects')` after success

    **Project mutations (`src/app/api/projects/[id]/route.ts`):**
    8. PATCH (update): `revalidatePath('/projects')` + `revalidatePath('/projects/' + slug)` after success. If slug changed, also revalidate old slug path.
    9. DELETE: `revalidatePath('/projects')` + `revalidatePath('/projects/' + slug)` after success

    **Project photo mutations (`src/app/api/projects/[id]/photos/route.ts`):**
    10. POST (add photos): `revalidatePath('/projects/' + slug)` after success (fetch project slug first)
    11. PUT (reorder): `revalidatePath('/projects/' + slug)` after success
    12. DELETE (remove photo): `revalidatePath('/projects/' + slug)` after success

    **Category mutations (`src/app/api/categories/route.ts`, `src/app/api/categories/[id]/route.ts`):**
    13. POST/PATCH/DELETE: `revalidatePath('/')` + `revalidatePath('/gallery')` after success (category changes affect homepage category cards and gallery filter tabs)

    **Critical:** Only call revalidatePath AFTER the mutation succeeds, never before. Place calls right before the success response return.
  </action>
