<task type="checkpoint:decision" gate="blocking">
  <decision>Choose photo storage and optimization approach</decision>
  <context>
    The roadmap flags this as a research question. The choice affects how images are stored, optimized, and served — and impacts all downstream phases (collections, CMS, deployment).

    Current state: 6 photos as static files in /public/photos/, referenced from photos.json. No optimization, no responsive images, same file for thumbnail and full-res.
  </context>
  <options>
    <option id="option-a">
      <name>Cloudinary (cloud-hosted optimization)</name>
      <pros>
        - Automatic responsive images via URL transforms (w_400, w_1200, etc.)
        - Automatic WebP/AVIF format negotiation
        - Free tier: 25GB storage, 25GB bandwidth/month — sufficient for portfolio
        - No build-time processing needed
        - Easy to add photos: upload to Cloudinary, add metadata to JSON
        - CDN-delivered globally
        - Supports blur-up placeholders via low-quality transform
      </pros>
      <cons>
        - External dependency (vendor lock-in for image URLs)
        - Requires Cloudinary account setup
        - Free tier limits could be hit if site gets significant traffic
        - Photos not self-hosted (less control)
      </cons>
    </option>
    <option id="option-b">
      <name>Local files + build-time optimization (sharp/vite-imagetools)</name>
      <pros>
        - Self-contained, no external dependencies
        - Full control over image pipeline
        - No bandwidth limits or vendor lock-in
        - Works offline during development
        - Images deployed alongside site
      </pros>
      <cons>
        - Build times increase with photo count (sharp processing)
        - Larger deployment bundle as photo count grows
        - Need to manage multiple image variants manually or via scripts
        - More complex setup (build scripts, output directories)
        - Vercel deployment size limits may become an issue with many photos
      </cons>
    </option>
    <option id="option-c">
      <name>Hybrid: Local originals + Cloudinary delivery</name>
      <pros>
        - Keep originals in repo for backup/portability
        - Cloudinary handles optimization and CDN
        - Best of both worlds for a portfolio that will grow
      </pros>
      <cons>
        - Repo size grows with originals
        - Two systems to manage
        - More complex than either pure approach
      </cons>
    </option>
  </options>
  <resume-signal>Select: option-a, option-b, or option-c (or describe your preference)</resume-signal>
</task>
